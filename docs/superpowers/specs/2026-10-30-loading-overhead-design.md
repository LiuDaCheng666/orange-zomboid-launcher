# 加载组件开销优化

用户已批准前一轮说明中的性能优化方向。本次沿用现有橙子、布局、配色、原生授权与取消操作；不引入新的设置、校验或等待任务，不改变服务器模组清单和加载顺序。

## 目的与操作路径
玩家仍从服务器卡片点击连接，经过现有选择后进入同一加载画面。优化只降低启动器附加在游戏加载上的开销。普通启动、服务器 Lua 重载、下载页和存档加载共用绘制实现，均须覆盖。

## 方案选择
1. 优先优化已有绘制路径：用真实字体与 OpenGL 基准找出文本截断和纹理绘制的开销；将错误摘要读取移出渲染线程。保留视觉与实际进度语义。采用此方案。
2. 改动游戏原生重载/并行加载：线程依赖与第三方模组兼容性不明确，本次不采用。
3. 仅隐藏错误或减少启用模组：不解决代码开销，也不符合用户意图，不采用。

## 设计
- 对长日志文本的截断，查明当前字体测量次数和实际耗时。采用有界的前缀搜索与小型缓存，保留最终适配宽度、中文和 Unicode 字符边界。
- Java 错误摘要目前由渲染线程同步检查并读取本地文件。通过单个按需后台读取器提供最近一次实际结果；读取频率仍约每 250ms，切换连接时不展示旧会话摘要，读取失败不阻断渲染。后台读取不参与启动器的全局任务锁。
- 不篡改真实内存、下载计数或日志含义，不降低动画目标帧数。

## 验证
先运行旧版基准，再写可失败的回归测试，然后实现并对比：长日志的字体测量次数、真实隐藏 OpenGL 场景每帧 CPU 时间，以及慢摘要读取时调用方是否仍立即返回。测量不是完整进服验收。
运行受影响的模型/真实游戏 Lua 与渲染上下文测试，并检查截图视觉不变。用候选程序的生产入口在隔离游戏与用户目录内验证启动、加载和退出；使用小窗口，不修改用户真实游戏、存档或前台设置。UI 截图交独立 Agent 审查。

## 边界
此前 54/106 秒来自游戏连接 Finish 至 Lua-connected 的整体时间，不能承诺全部消除。本次不能在没有现场线程采样时把 Windows+D 失效宣布为已修复。正式发布与覆盖 D 盘安装不在本次请求中。
