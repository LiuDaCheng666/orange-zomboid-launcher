Implemented backend/packaging only; Engine/controller/UI remain unbound for Task 3. Normal selections reference current mod roots. No full component payload is staged by this backend; only mandatory agent and pinned Buddy runtime are deployed into a new owned session. No real game entry, Steam/UI operation, release, version, server or website changes occurred.

## Consumer APIs

`new LauncherComponents(LauncherConfiguration context, Version gameVersion, Action<int,string> progress=null)` is instance-scoped. It never redirects Engine.Game/User. All browser-supplied selection must be resolved by Task 3 to native opaque source tokens; these explicit-path APIs are native-only.

- `Inspect(modRoot,id,token)` reads a **specific child of a mods directory**; `List(token)` lists selected records with current source identity/JAR/metadata and warning. A missing/invalid selected source remains visible with its specific warning. Reads do not initialize directories or acquire mutation locks. Progress gives actual selected-item counts; hash reads honor cancellation.
- `Select(modRoot,id,enabled,token)`, `SetEnabled(id,bool,token)`, `Uninstall(id,token)` mutate only `context.ComponentsDirectory/selection.json`. Uninstall removes selection, retains the managed identity exclusion, and leaves original payloads intact. These are not Steam installers. Known IDs and generic Java IDs use the same native selection API; explicit download/source lookup/acknowledgements remain Task 3.
- `Row` carries Id, Name, SourceRoot, Jar, Package, Sha256, **ApprovalStamp**, SourceEvidence, Enabled, Decision, Requires, LoadAfter, LoadBefore, Conflicts, Warning. `Decide(id,expectedStamp,allow,token)` takes **ApprovalStamp, not Sha256**: the token binds ID/root/JAR/package/hash so an old approval cannot authorize an identically hashed newly selected path. File updates return pending. State stores decisions privately under the context, and the next session projects only current approved selections into Buddy v2 approvals.
- `ManagedIds()` includes known managed IDs and previously selected generic IDs. `OrdinaryIds()` excludes them from the owned ordinary view. `SaveOrdinary(ids,token)` edits only the owned default list, preserves bytes for a no-op including unchanged imported component rows, and never enables/reorders component state. Component and ordinary writes use separate context-resource mutexes with finally-release; no global read lock.
- `CaptureCurrent(token)` provides one immutable-by-convention read transaction (Rows, Managed, Ordinary bytes, state stamp). `RequireCurrent(capture)` rejects changed state/default/source metadata. `PlanEnabled(ordinaryCatalog,token)` and its capture overload call existing `ModConfigurations.Order`; metadata, version ranges, safe payload paths and ZIP/package identity reuse existing helpers. The caller supplies its current ordinary catalog; available unique local Lua dependencies are included transitively in effective choices even when absent from ordinary checkboxes, without rewriting the persistent ordinary list. Java/managed dependencies still require explicit component source selection/approval; absent or ambiguous sources are not guessed. Absent ordinary metadata is not fabricated. Missing component dependencies/cycles/conflicts are returned in the existing SortResult. Task 3 owns exact-source download/retry and explicit selection of dependencies, rather than invoking legacy original-file installers.

`LiveModDiscovery.Prepare(components,ordinaryCatalog,token)` obtains authenticated `OrangeLive.jar` from BundledAssets. The native overload is `Prepare(components,byte[] liveAgent,ordinaryCatalog,token,bridgeRoot,string[] ordinaryOverride=null)`.

- Returns Session.Directory, Manifest, ManifestHash, VmArguments, EnabledIds, SelectedRoots and Warnings. Author order/conflict/cycle results are warnings, never blanket launch gates; invalid/missing selected payloads and concretely absent selected-component dependency IDs remain specific errors. Effective defaults preserve explicit ordinary relative order even when author order suggests a different arrangement. Insert VmArguments **before stock -cp/main**, preserving their order: mandatory live agent, then optional Buddy. Optional startup presentation follows these agents in Task 3.
- `ordinaryOverride=null` retains each runtime/save ActiveMods ordinary list; an array explicitly chooses a profile list, including an empty list. Components and their required IDs are merged into every runtime ActiveMods list with canonical deduplication, ordinary relative order retained, and full validated ordering anchors used for loadAfter/loadBefore placement. Disabled managed IDs are removed. ChooseGameInfo.Mod dependencies are never substituted by this live agent.
- The returned effective default/loaded files and safe Buddy config/approval files are per-session. The persistent ordinary default is never overwritten by preparation or game saveModsFile. Task 3 must explicitly own any desired post-game projection of in-game ordinary-editor changes back to the persistent configuration; no such lifecycle/UI is claimed here.
- Optional bridgeRoot must be inside this context; caller owns target nonce/expiry/bridge creation and lifecycle. Vanilla exposes only this explicit bridge if supplied, otherwise zero roots/IDs. It has no Buddy or component agent.
- Selected Java must be currently approved before preparation. A single capture feeds rows/order/managed IDs; preparation rechecks source JAR hashes and state/default/metadata before returning. Failed/cancelled session preparation removes only its own new session directory. Successful session cleanup and PID ownership belong to Task 3.
- Buddy runtime is exactly 2.3.4, SHA256 `eb79b9876332010733a8e0d7ce4fe0377846059a9e28859029e2a0fb449f6cf2`. Normal source updates are read live; unsupported Buddy builds are reported, not silently copied into this contract. Buddy3 numbered-only declarations explicitly report that this pinned runtime does not support them. B41 pages/source inspection remain available, but Prepare explicitly reports the unverified independent entry rather than claiming B41 live isolation or silently falling back.

Task 3 memory note: standalone Task1 3072 MB is a baseline. At production initialization preserve a valid safe user Xmx or use a real memory recommendation, without importing arbitrary original VM args. This task did not alter memory semantics.

## Runtime/build

Live Java sources are separate `LiveSource/ozl/environment`, sharing only read-only SafePaths/TargetContract compilation inputs. No OZLENV1/frozen source, source-resolution/runtime/preflight behavior was edited. The independent `OZLLIVE1` manifest uses Base64 UTF8 tab records: game/user/context/choices/vanilla, managed/selected, component/order/override/ordinary, jar(path/package/hash/approval), optional buddy(path/hash). Properties are `ozl.live.manifest` and `ozl.live.sha256`.

Discovery filters the game's current roots **on exit**, rechecking root/common/numeric-version mod identities each time, preserving ordinary Lua including unknown Java roots' Lua, removing every duplicate/disabled managed root, then adding selected current roots. Mixed managed identities fail specifically. Exact three choice methods redirect to session-owned files while cachedir/saves remain real. Vanilla clears runtime active lists.

Both actual Buddy `loadJar(Path,String,String,Phase)` and private `addJarToClasspath(Path,String,String)` are gated by canonical path, package, explicit decision and fresh SHA256. Pinned compiled Loader signatures and its sole append boundary are audited; target class provenance and early installation are checked. Byte-identical external JARs and unknown PREMAIN loads cannot inherit a selected hash's permission. This is not a sandbox for already approved Java.

Build-LiveComponent packages the agent, and Build-StartupComponent nests it at `ozl/live/LiveEnvironmentAgent.jar` inside the existing authenticated OrangeStartup asset. BundledAssets.ReadOwnAsset("OrangeLive.jar") extracts that exact entry with bounds/duplicate checks. ProductionSources registers both new C# files. Startup/environment build temporary directories were shortened to avoid actual Windows260 ByteBuddy extraction failure in this long worktree; frozen payload sources/semantics are unchanged. Generated ignored assets were rebuilt, not committed.
